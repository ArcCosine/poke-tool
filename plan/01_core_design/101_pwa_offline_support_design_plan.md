# 計画書: PWA化および完全オフライン対応の設計案

## 1. 概要
本プロジェクト（poke-tool）を PWA (Progressive Web App) 化し、ネットワーク接続がないオフライン環境下でも以下の操作を完全に利用可能にする：
1. アプリケーションの起動および各ページ（`/`, `/party`, `/ranking`, `/ev-calculator` 等）の閲覧・操作
2. 全ポケモンのアイコン・スプライト画像およびタイプ・カテゴリ画像の表示
3. ポケモン・技・持ち物・特性のマスターデータの検索・選択、ステータス計算、パーティ編成

---

## 2. PWA化のアーキテクチャと採用技術

### (1) `vite-plugin-pwa` (Workbox ベース)
Vite 環境における PWA 実装の標準ツール。
- Service Worker の自動生成とライフサイクル管理
- Web App Manifest (`manifest.webmanifest`) の自動生成
- オフライン用 HTML / JS / CSS の事前キャッシュ (Pre-caching)

### (2) キャッシュ戦略の設計

| リソース | キャッシュ戦略 | 説明 |
| :--- | :--- | :--- |
| **HTML / JS / CSS** | **Pre-cache (事前キャッシュ)** | アプリ起動時に全アセットを保存し、次回以降オフラインでも即時起動。 |
| **マスターデータ (`/data/*.json`)** | **StaleWhileRevalidate + IndexedDB** | 起動時はIndexedDB/キャッシュから即座に返し、オンライン時は裏で最新版を取得・更新。オフライン時はfetch失敗してもIndexedDBから確実に返却。 |
| **ポケモン画像 (`/assets/pokemon-sprites/*.png`)** | **CacheFirst (ランタイムまたは事前バックグラウンド)** | 一度読み込んだ画像は永続キャッシュ。完全オフライン化のため、初回起動完了後にバックグラウンドで全画像をプリフェッチする戦略を検討。 |
| **タイプ/カテゴリ画像 (`/assets/type-icons/`, `/assets/categories/`)** | **Pre-cache (事前キャッシュ)** | 合計100KB未満と軽量なため、Service Worker インストール時に即座に完全キャッシュ。 |

---

## 3. PWA化における懸念点と解決策

### 懸念点 1: ポケモンスプライト画像（44MB）のキャッシュ容量と初回通信量
- **課題**: 現在 341 体の画像があり、合計サイズが約 44MB ある。初回アクセス時に一括でダウンロードさせると、スマートフォンのギガ（モバイルデータ通信量）を圧迫し、初回読み込みが重くなるリスクがある。
- **解決策**:
  - **アプローチ A (推奨・段階的)**: 基本は `CacheFirst`（閲覧したポケモンから順次オフラインキャッシュ）とし、さらに設定画面やPWAバナー等で「**オフライン用データを一括ダウンロード (44MB)**」ボタンを提供する。ユーザーの意思でWi-Fi環境下等で一括キャッシュできるようにする。
  - **アプローチ B (画像最適化)**: 既存の PNG 画像（平均 130KB）を WebP 形式に変換・圧縮することで、画質を保ったまま約 5MB〜10MB 程度まで軽量化し、一括事前キャッシュを現実的なサイズにする。

### 懸念点 2: マスターデータ更新時のキャッシュの滞留 (キャッシュ無効化)
- **課題**: Service Worker が強力にキャッシュするため、新レギュレーションや新ポケモンが追加された際に「古いデータが表示され続ける」リスクがある。
- **解決策**:
  - Workbox のハッシュ付きリビジョン管理を利用。
  - アプリ内に「**新しいバージョンが利用可能です**」という通知トースト/ダイアログを表示し、ユーザーがクリックしてワンタップで最新版へリロード（`skipWaiting`）できる仕組みを実装。

### 懸念点 3: マルチページ (MPA) 構成におけるオフラインルーティング
- **課題**: 本アプリは MPA（`/party`, `/ranking`, `/ev-calculator` 等の個別 HTML）構成であるため、オフライン時に直接 URL（例: `/party`）を開いた際に 404 やオフライン画面になってしまう恐れがある。
- **解決策**:
  - ビルド時に生成される各 HTML（`index.html`, `party.html`, `ranking.html`, `ev-calculator.html` 等）をすべて Service Worker のプリキャッシュ対象に含める。

### 懸念点 4: iOS (Safari / WebKit) のストレージ削除ポリシー
- **課題**: iOS Safari では、数週間アクセスがないサイトの Cache Storage や Service Worker が自動クリーンアップされる場合がある。
- **解決策**:
  - ホーム画面に追加（PWAインストール）された状態であればクリーンアップの対象外になりやすい。
  - また、マスターデータは IndexedDB にも二重保持（IndexedDB は Cache Storage より生存期間が長い）することで、万一画像キャッシュが消えても計算機能や編成データは失われないように保護する。

### 懸念点 5: PWA マニフェスト用アプリアイコン (PNG形式) の不足
- **課題**: PWA としてインストール（ホーム画面追加）可能にするためには、192x192 および 512x512 の PNG アイコン（通常アイコンおよび maskable アイコン）が必須。現在は SVG のみ。
- **解決策**:
  - 既存の SVG アイコンから 192x192 および 512x512 の高解像度 PNG アイコンをビルドスクリプトまたは画像生成で用意する。

## 4. 推奨する実装ロードマップ

1. **Step 1: PWA アイコンおよび Web App Manifest の作成**
   - 192x192, 512x512 PNG アイコンの作成
   - `manifest.webmanifest`（アプリ名、テーマカラー、背景色、スタートURL、表示モード: `standalone`）の定義
2. **Step 2: `vite-plugin-pwa` の導入と Service Worker 設定**
   - HTML、CSS、JS、軽量アセット（タイプアイコン、マスターデータJSON）の Pre-cache 設定
   - ポケモン画像用の `CacheFirst` ランタイムキャッシュ戦略の設定
3. **Step 3: `db.ts` のオフライン耐性強化**
   - `fetch('/data/version.json')` がオフラインで失敗しても、IndexedDB にデータがあれば即座に返却するフォールバックロジックの実装
4. **Step 4: オフライン一括ダウンロード機能または画像最適化**
   - オフラインでも全341匹の画像を確実に表示させるためのキャッシュ機能の実装
5. **Step 5: 更新通知トーストUIとオフラインインジケーターの実装**
   - 新バージョン検知時の更新ボタン
   - ネットワーク接続状態（オンライン / オフライン）のステータス表示
