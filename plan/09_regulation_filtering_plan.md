# 計画書：レギュレーションM-AおよびM-Bのフィルタリング機能の追加と拡張設計

## 1. 目的
ポケモンチャンピオンズで利用可能なポケモンのフィルタリング機能として「レギュレーションM-A」と「レギュレーションM-B」を追加し、今後の追加レギュレーション（M-C以降など）にも容易に対応できる拡張性の高い設計を導入します。また、開発エージェントが将来簡単にレギュレーションを追加できるようにするための「レギュレーション追加スキル」を整備します。

## 2. 設計方針

### 2.1. 累積的レギュレーションの定義とデータ設計
レギュレーションは時系列で追加（累積）される傾向にあるため、以下のデータ構造で管理します。

1. **`src/data/regulations.json`（新規追加）**
   - UIで選択可能なレギュレーションの表示名や順序を多言語対応で定義します。
   - 例：
     ```json
     [
       { "id": "M-A", "name": { "ja": "レギュレーションM-A", "en": "Regulation M-A" } },
       { "id": "M-B", "name": { "ja": "レギュレーションM-B", "en": "Regulation M-B" } }
     ]
     ```

2. **`scripts/regulations_config.json`（更新）**
   - クローラーが使用するレギュレーションの判定ロジック用の構成ファイル。
   - 使用禁止（伝説など）の共通除外リストと、各レギュレーションで「新しく解禁（追加）されたポケモンのID」を管理します。
   - 例：
     ```json
     {
       "except_ids": [150, 382, 384, 483, 484, 1007, 1008],
       "regulations": {
         "M-A": {
           "description": "Regulation M-A: Initial pool",
           "new_pokemon_ids": []
         },
         "M-B": {
           "description": "Regulation M-B: Added M-B Pokémon",
           "new_pokemon_ids": [687, 689, 691, 861, 870, 904, 972, 979, 1000]
         }
       }
     }
     ```

3. **クローラーの判定ロジック（`scripts/fetch_pokeapi.ts` の更新）**
   - ポケモンIDが `except_ids` に含まれる場合は、すべてのレギュレーションで対象外（`[]`）とします。
   - 各レギュレーションでの解禁判定は以下のように行います。
     - レギュレーション順に累積していき、そのレギュレーション以前に解禁されたポケモンであれば、そのレギュレーションの `regulations` 配列に追加します。
     - M-A: M-B以降で新しく追加されたIDを除くすべての通常ポケモン。
     - M-B: M-C以降で新しく追加されたIDを除くすべての通常ポケモン（M-Aのポケモン ＋ M-Bで追加されたポケモン）。

### 2.2. UIの動的化（`src/components/StatSearch/StatSearch.tsx` の更新）
- レギュレーションの選択肢をハードコードせず、`src/data/regulations.json` から動的にロードしてプルダウンメニューを生成します。

### 2.3. 「レギュレーション追加スキル」の整備
1. **自動化スクリプト (`scripts/add_regulation.ts`)**
   - 以下の入力を受け取り、自動で `regulations.json` および `regulations_config.json` を更新してクローラーを実行するスクリプトを作成します。
     - 追加するレギュレーション名（例: `M-C`）
     - そのレギュレーションで新しく解禁されるポケモンIDの配列
2. **カスタムスキル (`skills/add-regulation/SKILL.md`)**
   - 将来のエージェント向けに、新しいレギュレーションを追加する際の手順とスクリプトの実行方法を詳細にドキュメント化します。
